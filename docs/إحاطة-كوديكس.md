## ٣. البنية التقنية (Stack)

- **الإطار:** Astro 6 + جزر React 18 + Tailwind 4 — موقع ثابت (SSG) يُبنى بـ`npm run build` (~63 صفحة).
- **قاعدة البيانات:** Firebase Firestore (مشروع `brandzo-erp-2026`، خطة **Spark المجانية** — لا Cloud Functions ولا نسخ مجدول حتى الترقية لـBlaze). المصادقة Firebase Auth. **Firestore هو مصدر الحقيقة** (قرار محسوم §19).
- **الأمن:** `firestore.rules` في جذر الريبو (محكمة، ~123 اختبار قواعد) — **الوكلاء يعدّلونها في الريبو، المالك وحده ينشرها من Console**.
- **الاختبارات:** `npm test` = `node --test` على `src/**/*.test.js` — **~728 اختبارًا كلها خضراء** ويجب أن تبقى كذلك.
- **حارس إضافي:** `npm run audit` (تدقيق سلامة البوابة) — يجب أن يمرّ قبل أي دفع.
- **اللينت:** `npm run lint` — **خط الأساس أحمر أصلًا على مستوى الريبو**؛ يُحكم على **المشاكل الجديدة فقط** (لا تحاول تصفير القديم).
- **prebuild تلقائي:** `scripts/build-arch.mjs` (يولّد خريطة المعمارية `architecture.json` + `arch-wiki`) و`scripts/build-org.mjs` (يولّد كتالوج الوظائف والتقارير من `org-structure.json`).
- **أوفلاين 100%:** PWA + خط IBM Plex Sans Arabic مستضاف ذاتيًّا — **ممنوع أي CDN أو Google Fonts**.
- **مختبر أودو محلي:** `C:\brandzo-odoo` — Odoo 19 حقيقي على Docker (localhost:8069، قاعدة `brandzo`، admin/12345678) + موديول `brandzo_warehouse` في مجلد `brandzo-addons/` (52/52 اختبارًا خضراء عليه).

### خريطة المجلدات المهمة
```
src/pages/dashboard/   ← ~55 شاشة لوحة (كل شاشة صفحة Astro تستضيف جزيرة React)
src/components/        ← مكوّنات React (odoo/ = مكوّنات نظام تصميم أودو، pwa/، ui/، brandzo-erp/)
src/services/          ← المنطق الخالص + خدمات Firestore (هنا معظم الاختبارات)
src/data/              ← مصادر JSON واحدة (org-structure.json · reference-crosswalk.json · nav)
src/config/navCatalog  ← مصدر التنقّل الوحيد للبوابة كلها
firestore.rules        ← قواعد الأمن (تعديل هنا، نشر عند المالك)
docs/                  ← الخطط الحاكمة · scripts/ ← المولّدات · brandzo-addons/ ← موديول أودو
```

## ٤. ما نُفّذ حتى الآن (مكتمل وحيّ)

1. **محرّك المستندات المحكوم** — `/dashboard/documents`: **27 نموذجًا مستنديًّا** في 7 سلاسل (شراء PO/GRN، بيع، نقل TRN/DN/POD، مرتجعات RET/SRN، تلف DMG، جرد CC، حاويات CTR…) بترقيم تسلسلي بعدّادات ذرّية، مرفقات مضغوطة بالمتصفح، طبقة رقابة/مطابقة، مطابقة ثلاثية، 5 حرّاس، صندوق اعتماد، ربط تسلسلي `docref`.
2. **دفتر الحركات المخزني** — `stock_moves` ملحق-فقط يُقيَّد عند «منجَز» + أرصدة ذرّية + حجز فعلي + FEFO + `/dashboard/stock-ledger`.
3. **ماستر الأصناف** — مصدر سحابي واحد + استيراد Excel + باركود (ماسح آيفون) + أرصدة FEFO + أصناف معلّقة للمراجعة + الجرد الذكي (`stock-operations`).
4. **ماستر شركاء الأعمال** — موردون + عملاء (محرّك موحّد + استيراد بمعاينة + أرشفة) + تحليل إنفاق الموردين + لوحة KPIs.
5. **سلاسل الإمداد** — رحلات TRIP · أوامر صيانة WO · عُهد CUST · لوحة تنفيذية · **جرد المركبات** (23 مركبة، دور fleet) · رصيد مخزون لكل مركبة (DN يحمّل، POD يخصم).
6. **الهيكل والتوظيف** — مصدر واحد `org-structure.json` (36 وظيفة بمتطلباتها، 13 دورًا) يولّد التقارير والكتالوج · توظيف ذكي (CV سحابي) · **تسكين** المرشحين في المناصب (`assignments` ملحق-فقط) · ملف تعريفي للموظف · CRUD أدوار من الواجهة.
7. **لوحة عمالة الشحن والتفريغ** — `/dashboard/labor-operations`: دور `labor_supervisor` · أطقم `crews` · مهام موقوتة `labor_tasks` (تتبّع زمني بـserverTimestamp) · مستند حاوية CTR.
8. **جسر المزامنة الحي مع أودو** — `/dashboard/odoo-sync`: يدفع **كل المستندات الـ27 + العمليات المخزنية** إلى نماذج أودو (جدول عبور `docCrosswalk` يحرسه اختبار انجراف) **مسوّدةً حتى الاعتماد** عبر نفس واجهة عميل الإنتاج (`odoo.create/write/searchRead`) + سحب عكسي للأصناف + onSnapshot + إشعارات. اعتماد PO يولّد استلامًا واردًا WH/IN تلقائيًّا (محاكاة سلوك أودو الحرفي).
9. **موديول أودو حقيقي** — `brandzo_warehouse` (7 حرّاس، 52 اختبارًا) يعمل حيًّا على Odoo 19 في المختبر المحلي + قمرة Tier-1 (`RealOdooCockpit`، 14 رابطًا عميقًا).
10. **نظام إسناد المهام السحابي** — `/dashboard/tasks`: إسناد لمستخدم فعلي + توثيق ملحق-فقط + ردّ + حالات تنفيذ + معدّل استجابة.
11. **مساعد الاجتماعات** — تسجيل صوتي + تفريغ عربي حي + **تفريغ ملفات صوت بأي مدّة داخل المتصفح** (Whisper عبر WebGPU، بلا اشتراكات) + أداة محاضر موحّدة (`MeetingsApp`) + أرشيف دوري بترقيم BFP-SCM-PR.
12. **الهوية والتصميم** — ثيم `bz-light` بمظهر أودو (اللون `#714B67`) + نظام مكوّنات أودو (ListView/FormSheet/Badge…) + خط IBM Plex Sans Arabic ذاتي الاستضافة + PWA أوفلاين + زر الرجوع يغلق أي طبقة (`overlayHistory`).
13. **الحوكمة والتقارير** — المرجع الرسمي مطابَق 100% مع البوابة (crosswalk مصدر واحد: 24 نموذجًا/7 سلاسل/9 حرّاس) + تقارير UAT (82 معيارًا) وquality وvalue + دراسة مقارنة عالمية (نضج 2.9/5) + حزمة استعداد ديلويت (TOM + KPIs).

### قيد العمل / خطط معتمدة
- **حزمة تقارير المتطلبات BFP-SCM-REQ-2026** (إحالة + 6 تقارير) — **الموعد الحاكم: تسليم تحليل الدورة للميزان السبت 2026-08-08**.

## ٦. القواعد الحاكمة (غير قابلة للتفاوض)

1. **العربية** لغة التخاطب مع المالك حصرًا (الكود والكوميتات والواجهات كما هي).
2. **بلا إيموجي في الواجهات** — أيقونات خطية SVG فقط. **الأحمر للتحذير فقط** — لا يُستخدم زخرفةً.
3. **بنية 3 طبقات لكل لوحة**: تدخّل الآن ← إجراءات سريعة ← فهرس كامل.
4. **لا حذف ولا تغيير لأي URL قائم** — الربط قبل الإضافة، و`navCatalog` مصدر التنقّل الوحيد.
5. **الأنماط الملحقة-فقط مقدّسة**: `audit` · `scans` · `events` · `stock_moves` · `assignments` · `control` · `attachments` — لا تعديل ولا حذف على سجلاتها أبدًا.
6. **تحقّق قبل الثقة**: لا تُصدر حكمًا على حالة النظام من الوثائق وحدها — راجع git والكود الفعلي أولًا.
7. **البوابة الخضراء قبل أي دفع**: `npm run build` ✓ + `npm test` ✓ (كل الاختبارات) + `npm run audit` ✓ + لا مشاكل لينت **جديدة**.
8. **لا CDN** — كل الأصول ذاتية الاستضافة (قاعدة الأوفلاين).
9. أرقام لاتينية في الواجهات · خط IBM Plex Sans Arabic · هوية أودو `#714B67`.
10. **المراسلات الرسمية**: بالتوقيعين المعتمدين PNG (محمد البرشي · رمزي الباش — مدير الخدمات اللوجستية) وبالرقم الإشاري BFP-SCM-PR — لا تلفيق توقيع أبدًا.

## ٧. توحيد الذاكرة — بروتوكول العقل المشترك

**المبدأ: الريبو نفسه هو الذاكرة المشتركة الوحيدة.** لا ذاكرة خاصة بوكيل تحمل حقيقة لا يعرفها الآخران.

### طبقات الذاكرة المشتركة
| الملف | دوره | من يقرؤه |
|---|---|---|
| `AGENTS.md` (جذر الريبو) | دستور التشغيل المضغوط — **يقرؤه Codex تلقائيًّا كل جلسة** | Codex آليًّا · Claude والمالك مرجعًا |
| `SESSION_HANDOFF.md` (رأس الملف) | **أين توقّفنا · ماذا فعلنا · ما التالي** — الذاكرة الحيّة | الجميع، أول كل جلسة |
| `ROADMAP.md` | الخطة الأم والمعمارية | عند التخطيط |
| `docs/` | الخطط التفصيلية المعتمدة | قبل العمل في نطاقها |
| `architecture.json` / `arch-wiki` | خريطة آلية تتولّد مع كل بناء | للاستكشاف السريع |

### طقس بداية كل جلسة (لكلا الوكيلين)
1. `git pull` (أو مزامنة الفرع) — **لا عمل على نسخة قديمة أبدًا**.
2. اقرأ رأس `SESSION_HANDOFF.md` (سطر «آخر تحديث» + قسم «أين توقّفنا»).
3. اقرأ `AGENTS.md` (يحدث تلقائيًّا عند Codex).

### طقس نهاية كل مهمة
1. البوابة الخضراء (بند 7 أعلاه).
2. **حدّث رأس `SESSION_HANDOFF.md`** بمدخل جديد **موسومًا بهويتك**: `[Codex]` أو `[Claude]` + التاريخ + ما أُنجز + ما تبقّى.
3. كومِت برسالة عربية بصيغة المشروع: `feat(نطاق): وصف` — وذيّلها بسطر الهوية (`Co-Authored-By: Codex <...>` أو ما يعادله).
4. **الدفع لـ`main` بأمر المالك فقط** («ارفع»).

### تقسيم العمل ومنع التصادم
- **المالك هو الموجّه**: مهمة واحدة → وكيل واحد. لا يعمل الوكيلان على الملفات نفسها بالتوازي.
- عمل Codex يبدأ في فروع `codex/*` (وClaude في `claude/*`)، والدمج لـ`main` بقرار المالك.
- إن وجدتَ في `SESSION_HANDOFF.md` مدخلًا `[Claude]` عن عمل جارٍ غير مرفوع — **لا تلمس نطاقه** واسأل المالك.
- الخلاف الفني لا يُحسم بين الوكيلين — يُعرض على المالك بخيارات واضحة وتوصية.
