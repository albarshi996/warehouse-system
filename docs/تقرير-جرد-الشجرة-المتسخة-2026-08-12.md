## 5. المرجع Git المعطوب

المرجع الذي يراه Git غير صالح هو:

```text
refs/codex/turn-diffs/checkpoints/4714621e598f5ccb077f317b7adff39895d40c1bee2d74cdbe321776a94ab397/769cca8772bbffc1ea0f659da65dd5eea0b2080c60c5048723a7fab99a635da5/1786529029919/ce36201f-8a79-4dc0-b4e3-a94b2e64e8e8
```

ويظهر بقيمة:

```text
0000000000000000000000000000000000000000
```

الآثار المثبتة:

- `git show-ref` يفشل بـ128: `bad ref`.
- `git fsck --full --no-reflogs` يفشل بـ2: `invalid sha1 pointer`.
- محاولة `fetch/pull` في worktree المشتركة فشلت سابقًا لأن الخادم لا يستطيع تلبية كائن مرتبط بهذا المرجع.
- فحص المسار الفيزيائي أعاده أحيانًا «غير موجود» بينما `show-ref` يراه؛ وهذا يرجح سباق إنشاء/حذف من آلية checkpoint. لذلك لا يجوز حذف مسار محسوب بصورة عمياء أثناء عمل Codex عليه.

### إصلاحه الآمن — بعد موافقة منفصلة

1. إيقاف/إغلاق أي مهمة Codex تستخدم مستودع Git المشترك، مع إبقاء النسخة النظيفة الحالية مستقلة.
2. إعادة `git show-ref` والتأكد أن **نفس المرجع** ونفس القيمة الصفرية هما العطل الوحيد.
3. إن كان ملف المرجع موجودًا فعليًا: نسخ الملف الواحد إلى حجر صحي خارج `.git` مع مساره ووقته، ثم إزالة **ذلك الملف فقط**؛ لا حذف مجلد checkpoint ولا استخدام wildcard.
4. إعادة `git show-ref` ثم `git fsck --full --no-reflogs`.
5. إذا أصبحا سليمين: `git fetch --prune`، ثم التحقق من `refs/remotes/origin/main`.
6. إذا أعادت آلية Codex إنشاء المرجع الصفري، يتوقف التنظيف ويُعالج مصدر checkpoint أولًا؛ لا نكرر الحذف.

هذا التغيير يمس `.git`، ولذلك لم يُنفذ في هذه الجلسة رغم أن المرجع لا يشير إلى كومِت صالح.

## 8. قرار التنفيذ التالي

لا يحتاج تطوير نسخة العميل انتظار تنظيف الأصل؛ النسخة النظيفة تحميه. أما تنفيذ تنظيف الأصل فعليًا فيحتاج موافقة المالك على مرحلتين منفصلتين:

1. **إصلاح المرجع الصفري الواحد** بعد إيقاف مستخدمي Git المشترك.

حتى ذلك الحين، أفضل معنى لـ«تنظيف بلا انهيار» هو: لا نمس الأصل، ننقل النية إلى الفرع النظيف، ونزيل لاحقًا النسخ المؤكدة فقط واحدةً واحدةً.
