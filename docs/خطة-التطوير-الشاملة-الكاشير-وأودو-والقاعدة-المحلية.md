## ٠) الملخّص التنفيذي — هل «كل شيء سليم»؟

**الحكم الصادق:** النظام **سليمٌ بنيويًّا ومتقدّم** — لا انهيار ولا خطر وشيك. البوابة خضراء: **٦٥٧ اختبار وحدة + اختبار قواعد بالمحاكي**، حاجزا نشرٍ صلبان (`npm test` + `npm run audit`)، قواعد أمان **مشدّدة ومُختبَرة** (لا مجموعة مفتوحة للعموم، لا تصعيد أدوار)، وأوفلاين حقيقيّ عبر PWA مثبَّت. الفجوات ليست أعطالًا حرجة بل من ثلاثة أصناف:

1. **ثغرات سلامة بيانات** (integrity) لا سرّية — أخطرها ثغرة مكتبة `xlsx` معروفة يصل إليها المستخدم.
2. **ميزة الكاشير/POS غير موجودة إطلاقًا** — دورة البيع الحاليّة مستنديّة (SO→PICK→DN→INV) لا لحظيّة.
3. **تكامل أودو جاهزٌ لكن غير موصول** — طبقة كاملة معزولة، والمزامنة كلّها تصميمٌ بلا تنفيذ.

|---|---|---|
| **صحّة الكود** | ٦٥٧ اختبارًا · حاجزان صلبان · لينت ١٢٤ (٥٣ خطأ/٧١ إنذار، غالبها ضجيج CDN) | ✅ سليم |

## ٣) خاصّية الكاشير (POS) — التصميم والمراحل

### ٣-أ) لماذا بناءٌ جديد؟
دورة البيع الحاليّة **مستنديّة**: أمر بيع (SO) → تجهيز (PICK) → إذن تسليم (DN، **هنا يُخصم المخزون فعلًا**) → فاتورة (INV). هذه دورةٌ رقابيّة بطيئة لا تصلح لنقطة بيعٍ تخصم لحظيًّا. الكاشير يحتاج مسارًا مضغوطًا: **امسح → أضِف للسلّة → استلم الدفع → اخصم المخزون الآن → اطبع الإيصال**.

### ٣-ب) ما هو موجود للبناء عليه (لا نبدأ من الصفر)
| المكوّن الجاهز | الموضع | الدور في الكاشير |
|---|---|---|
| `lookupByBarcode` | `itemService.js` | قلب الكاشير: باركود → صنف بسعره ووحدته |
| المعاملة الذرّية للبيع | `ledger/salesService.js` (`allocateAndReserve` داخل `runTransaction`) | نمطٌ جاهز يُنسخ إلى «بيع فوريّ يخصم لحظيًّا» |
| الأرصدة والحجوزات | `balancesService.js` + `ledger/reservations.js` | المتاح = qty − reserved (حارس عدم البيع تحت الصفر) |
| قاعدة خصم DN | `ledger/postingRules.js` | الكاشير يعيد استخدامها مضغوطةً في خطوة واحدة (قاعدة قيد `POS`) |
| حقول السعر/الخصم/الضريبة | `schemas/so.js` + `schemas/inv.js` | أساس بنود السلّة (سعر · خصم بند/فاتورة · نسبة/قيمة ضريبة · إجماليّات) |
| نمط السجلّ الملحق-فقط | `stock/scanMerge.js` | **أقرب نمط قائم لـ«جلسة/درج كاشير»** (سجل أحداث لا يُعدَّل، مجموع الأحداث = الحالة) |
| مكتبات الباركود | `public/lib/` (html5-qrcode · JsBarcode) | طبقة المسح جاهزة |

### ٣-ج) الإصلاح المُمكِّن الأوّل (صغير وحرج)
**تفعيل سعر البيع:** حقل `sellPrice` يُستورَد اليوم لكن **لا يُقرأ في أيّ منطق** — كل الحسابات تستعمل التكلفة (`unitPrice`/`costPrice`). أوّل خطوة: قراءة `sellPrice` في `lookupByBarcode` (مع سقوطٍ آمن للتكلفة عند غيابه). بلا هذا لا يوجد سعر بيع فاعل.

### ٣-د) نموذج البيانات المقترح (مجموعتان جديدتان)
```
pos_sessions/{sessionId}          ← جلسة/وردية كاشير (ملحق-فقط بنمط scanMerge)
  cashierUid · terminalId · openedAt · openingFloat
  events[]: {sale|cash_in|cash_out|no_sale}   ← لا يُعدَّل حدثٌ بعد قيده
  closedAt · countedCash · expectedCash · variance

pos_orders/{orderId}              ← أمر بيع لحظيّ
  sessionId · lines[{sku, qty, sellPrice, lineDiscount, lineTotal}]
  invoiceDiscount · taxRate · taxValue · grandTotal
  payments[{method: cash|card|transfer, amount}]   ← دفع مُجزّأ
  changeDue · status: paid|refunded
  idempotencyKey   ← معرّف محلّيّ يمنع الازدواج عند المزامنة الأوفلاين
  stockPosted: bool   ← ختم الخصم الذرّي
```
- **الخصم الذرّي:** عند «استلام الدفع» تُنفَّذ معاملة `runTransaction` واحدة: تتحقّق المتاح (FEFO)، تخصم الرصيد، تقيّد حركة `stock_move` من نوع `POS-OUT`، وتختم `stockPosted`. مفتاح `idempotencyKey` يمنع الخصم المزدوج.
- **قواعد Firestore:** مجموعتان جديدتان بقاعدتَي أمان (كتابة للكاشير النشط فقط · `pos_sessions` ملحق-فقط · لا تعديل بعد الإغلاق) — يفرضها حاجز `audit-portal.mjs` (يرفض مجموعة بلا قاعدة).

### ٣-هـ) مراحل التنفيذ
| مرحلة | المخرج | الاعتماد |
|---|---|---|
| **٣-١** | تفعيل `sellPrice` + قاعدة قيد `POS` (خصم فوريّ ذرّيّ) + اختبارات | — (داخليّ) |
| **٣-٢** | واجهة كاشير لمسيّة: بحث/مسح فوريّ · سلّة · خصم/ضريبة على السطر والأمر · شاشة دفع (نقد/بطاقة/تحويل + باقٍ + دفع مُجزّأ) | ٣-١ |
| **٣-٣** | جلسة/وردية + درج نقديّة (فتح برصيد افتتاحيّ · حركات نقد · تقفيل بمطابقة `expected/counted/variance`) | ٣-٢ |
| **٣-٤** | إيصال حراريّ ٨٠مم (قالب مستقلّ عن A4) + تقارير المبيعات اليوميّة للوردية | ٣-٢ |
| **٣-٥** | وضع بيع أوفلاين: طابور مبيعات محلّيّ + مزامنة لاحقة بمفتاح idempotency | ٣-٣ + طبقة الأجهزة (القسم ٤) |

## ٤) أجهزة البيع المباشر — طبقة الأجهزة الطرفيّة

> «الكاشير» برمجيّة، و«أجهزة البيع المباشر» هي العتاد الطرفيّ: الماسح · الطابعة الحراريّة · الدرج النقديّ · شاشة العميل · قارئ البطاقة. الويب يفرض قيودًا يجب تصميم الحلّ حولها.

| الجهاز | الحالة | الخيار المقترح |
|---|---|---|
| **ماسح الباركود** | ✅ جاهز | يعمل كـ«لوحة مفاتيح» (keyboard-wedge) أو كاميرا عبر `html5-qrcode` الموجود |
| **الطابعة الحراريّة ٨٠مم** | 🔴 غير موجود | **المرحلة أ:** طباعة المتصفّح بقالب CSS ٨٠مم (`window.print`) — تعمل على أي نظام/طابعة، بلا تبعيّات. **المرحلة ب:** WebSerial/WebUSB بأوامر ESC/POS للطباعة المباشرة (كروم/سطح مكتب فقط) |
| **الدرج النقديّ** | 🔴 غير موجود | يُفتح بنبضة من الطابعة (ESC/POS pulse) → يتطلّب WebSerial/WebUSB أو **جسرًا محلّيًّا (Tauri/عميل صغير)** |
| **شاشة العميل** | 🔴 غير موجود | نافذة/تبويب ثانٍ يعرض الإجمالي (بسيط) |
| **قارئ البطاقة** | 🔴 غير موجود | خارج نطاق الويب المباشر — يُسجَّل الدفع يدويًّا أو عبر مزوّد خارجيّ لاحقًا |

### التوصية المرحليّة لطبقة الأجهزة
1. **المرحلة أ (فوريّة، تعمل في كل مكان):** إيصال ٨٠مم بطباعة المتصفّح. لا درج، لا تبعيّات — تكفي لأغلب نقاط البيع.
2. **المرحلة ب (كروم/سطح مكتب):** WebSerial/WebUSB → طباعة ESC/POS مباشرة + فتح الدرج بنبضة.
3. **المرحلة ج (المحطّة المتكاملة):** تغليف التطبيق بـ **Tauri** (أو Electron) → مثبِّت `.exe`/`.apk` حقيقيّ + وصولٌ كامل للأجهزة + أوفلاين متين. **هذه المرحلة تلتقي مباشرةً مع القسم ٧ (النسخة المحلّية القابلة للتثبيت).**

  |---|---|

  | PR (طلب شراء) | `purchase.requisition` |

## ٦) المزامنة — الدوريّة (periodic) واللحظيّة (real-time)

> ثلاث مراحل من وثيقة العقد، **لا شيء منها منفَّذ بعد**. أرتّبها من الممكن اليوم إلى المشروط باستضافة أودو.

### المرحلة ١ — سحبٌ دوريّ (Periodic Polling) ✅ تعمل على Spark
- `syncService` (يُكتَب) يسأل أودو كل فترة عن `write_date > lastSync`.
- المؤشّر `lastSync` في وثيقة `sync_state` (Firestore) + مرايا قراءة `odoo_mirror_*` + **قواعد أمان جديدة لها**.
- **المُشغِّل (نقطة القرار):** خطّة Spark بلا Cloud Functions → خياران: (أ) **Cloudflare Cron Trigger** على الوسيط (الأنظف)، أو (ب) مؤقّت في المتصفّح عند فتح تبويب مديرٍ (بديل بلا بنية).
- **هذه هي «التحديث الدوريّ» المطلوب** — بسيطة وكافية للبداية.

### المرحلة ٢ — دفعٌ من البوابة (Outbox) — إرسال المستندات
- عند بلوغ مستندٍ حاكم حالة **«منجَز»** يُقيَّد في طابور `sync_outbox` (Firestore).
- `syncService` يدفعه عبر الوسيط: `odoo.create('purchase.order' | 'stock.picking' | 'account.move', mapper(doc))`.
- **مفتاح منع التكرار (idempotency) = معرّف مستند Firestore** → لا ازدواج عند إعادة المحاولة.
- **هذا هو مسار «إرسال المستندات إلى أودو»** — ويحتاج توسعة المُطابِق (٥-ج/٢) أوّلًا.

### المرحلة ٣ — لحظيّة حقيقيّة (Real-time Webhooks) 🔴 مشروطة باستضافة أودو عامّة
- Webhooks من `base_automation` في أودو ١٩ → الوسيط يستقبل ويكتب في Firestore عبر REST بحساب خدمة → **يُلغي الـpolling**.
- **الشرط الحاكم:** أودو على عنوان عامّ (المختبر اليوم `localhost:8069` فقط — الوسيط السحابيّ لا يراه). **قرار مالك: توقيت استضافة أودو حقيقيّة.**
- حتى ذلك الحين: «شبه لحظيّ» عبر polling قصير + دفع Outbox فور «منجَز».

### التعارضات والنسخ الاحتياطيّ
- **سياسة التعارض:** «الأحدث يكسب + سجلّ تعارض» يُعرض في شاشة «مراقبة المزامنة» (تُبنى بنمط أودو `ListView`).
- **قاعدة أودو (PostgreSQL):** `pg_dump` يوميّ مجدول + لقطة قبل أي ترقية + هجرة لا مسح + **تمرين استعادة شهريّ** (النسخة التي لم تُجرَّب استعادتها ليست نسخة).

## ٧) قاعدة البيانات المحلّية القابلة للتثبيت (نسخة setup على الأجهزة)

### ٧-أ) ما هو قائمٌ فعلًا (٨٠٪ من الهدف مُنجَز)
- التطبيق **PWA قابل للتثبيت** بالفعل: `manifest.webmanifest` (`display:standalone`، أيقونات 192/512/maskable، RTL) + Service Worker مولَّد بعد كل بناء (precache للهيكل · `networkFirst` للصفحات · `cacheFirst` للأصول · صفحة «غير متّصل»).
- **كاش Firestore دائم** (`persistentLocalCache` + دعم تبويبات) → قراءة أوفلاين + **طابور كتابة يُدفع تلقائيًّا** عند عودة الشبكة.
- **القيد الوحيد:** أوّل تسجيل دخول على كلّ جهاز يجب أن يكون **متّصلًا** (`signInWithEmailAndPassword`)؛ بعده تبقى الجلسة محليًّا ويعمل أوفلاين.

### ٧-ب) تقوية منخفضة الكلفة (تُنجَز الآن)
1. `cacheSizeBytes: CACHE_SIZE_UNLIMITED` في `firebase.js` (اليوم سقف ~٤٠م.ب مع طرد الأقدم).
2. خطوة **«تسخين مُسبق»** بعد الدخول تسحب مجموعات الدور (فيتوفّر ما يلزم أوفلاين لا ما جُلب صدفةً).
3. **معالجة رفض الكتابة عند العودة** برسالة واضحة (كتابةٌ أوفلاين تخالف القواعد تُرفَض وتُرتجَع صمتًا اليوم).
4. توثيق «أوّل دخول أونلاين» في دليل التشغيل.

### ٧-ج) الاستقلال الكامل عن السحابة (للمحطّة المنعزلة — كلفة عالية)
لجهازٍ يعمل **بلا إنترنت إطلاقًا** (مثل محطّة كاشير في موقعٍ بلا شبكة):

| الخيار | الجدوى | الكلفة |
|---|---|---|
| **PWA مثبَّت (الحاليّ)** | ✅ قائم | ~صفر (لكنه سحابيّ-أوّلًا) |
| **Tauri/Electron + SQLite محلّيّة مصدرًا للحقيقة + طبقة مزامنة** | ✅ الاستقلال الحقيقيّ + مثبِّت `.exe` + وصول الأجهزة (يخدم القسم ٤) | **عالية** — يشترط طبقة التجريد (القسم ٨) أوّلًا |
| **IndexedDB محلّيّ خلف Repository** | ✅ استقلال ضمن المتصفّح | عالية |

**التوصية:** للهدف القريب (كاشير مثبَّت يعمل أوفلاين) تكفي **المرحلة أ+ب** (PWA مقوّى، ثم Tauri عند الحاجة لدرجٍ وطابعة). الاستقلال الكامل يُجدوَل بعد بناء طبقة الـRepository (القسم ٨).

## ٨) آليّة تبديل قاعدة البيانات

### ٨-أ) العائق الحقيقيّ
لا توجد **أيّ طبقة عزل**: Firestore خام في **١٥١ موضعًا عبر ٢٥ ملفًّا**، و**٥٩ مستمع `onSnapshot`** حيّ، والأخطر أن **منطق العمل نفسه يعيش في `firestore.rules` (٦٠٧ أسطر)** لا في JS — بوّابات الاعتماد، اللاتعديل، «الرقم مرّة واحدة». تبديل المزوّد اليوم يعني إعادة كتابة ١٥١ موضعًا + إعادة إنتاج الدلالات الذرّية (`runTransaction`/`increment`/`serverTimestamp`) + إعادة بناء ٥٩ اشتراكًا + **إعادة بناء منطق القواعد بالكامل** في طبقة إلزام مكافئة.

### ٨-ب) القالب الجاهز داخل المشروع
النمط الصحيح **موجود بالفعل** لأودو (`odoo/index.js`): واجهة واحدة تُختار بمتغيّر بيئة.
```js
export const odoo = isProduction ? realOdooClient : mockOdooClient;   // odoo/index.js:24
```
Firestore لا تملك نظيرًا — إنها خام ومنتشرة. نطبّق النمط ذاته على مرحلتين:

### ٨-ج) الخطة على مرحلتين
**المرحلة ١ — إدخال طبقة Repository (شرط مسبق):**
أنشئ `src/services/db/` بمستودعات لكل مجموعة (`itemsRepo` · `ledgerRepo` · `documentsRepo` · `balancesRepo` …) تُخفي بدائيّات Firestore، فتنتقل الـ١٥١ موضعًا خلف ~١٥ وحدة. **يُنجَز تدريجيًّا** — نبدأ بالمجموعات التي يلمسها الكاشير (الأصناف · الأرصدة · الدفتر) فيخدم القسمين ٣ و٧ معًا.

**المرحلة ٢ — مُبدِّل المزوّد بنمط أودو:**
```js
// src/services/db/index.js  (على غرار odoo/index.js:24)
export const store = PROVIDER === 'firestore' ? firestoreStore : localStore;   // PUBLIC_DB_PROVIDER
```

**العوائق التي يجب أن يحلّها أي مزوّد بديل:** الاشتراك الحيّ (وإلّا استقصاء)، الذرّية (`runTransaction`/`increment` شرط صحّة لا رفاهية)، وطبقة إلزامٍ تكافئ `firestore.rules` (وإلّا هبطت الضمانات إلى عميلٍ يُتجاوَز). أما المصادقة فيمكن إبقاء Firebase Auth مع تبديل القاعدة، أو هويّة محلّية للمزوّد المنعزل.

| **الموجة ٥ — توصيل أودو والمزامنة الدوريّة** | توصيل العميل + اختبار تكامل (٥-ج/١) · توسعة المُطابِق (٥-ج/٢) · نشر الوسيط · مزامنة ١ polling (٦-١) · مزامنة ٢ outbox لإرسال المستندات (٦-٢) | **حساب Cloudflare (المالك)** | تحديث دوريّ + إرسال المستندات لأودو |
| **الموجة ٦ — المزامنة اللحظيّة** | Webhooks (٦-٣) + شاشة مراقبة المزامنة + `pg_dump` وتمرين استعادة | **استضافة أودو عامّة (قرار المالك)** | مزامنة لحظيّة حقيقيّة |
| **الموجة ٧ — طبقة القاعدة الاستراتيجيّة** | طبقة Repository تدريجيًّا (٨-ج/١) بدءًا بمجموعات الكاشير · مُبدِّل `PUBLIC_DB_PROVIDER` (٨-ج/٢) | لا شيء | يفتح تبديل القاعدة والمزوّد المحلّي المنعزل |

**الملاحظة الحاكمة:** الموجات ١→٤ **لا تعتمد على أحد** ويمكن إنجازها فورًا وتسلّم أثمن ما طلبته (الكاشير العامل). الموجتان ٥→٦ (أودو اللحظيّ) مشروطتان بقرارَي المالك. الموجة ٧ استثمارٌ استراتيجيّ يُجدوَل بعد استقرار الكاشير.

## ١٠) ما يلزم المالك — قرارات وحسابات

### قرارات تحتاج حسمك (مع توصيتي)
1. **نطاق الكاشير أوّلًا:** أوصي بـ**الموجة ٢ كاملة** (كاشير عامل بإيصال طباعة متصفّح) قبل الاستثمار في الدرج/ESC/POS — قيمةٌ فوريّة بلا عتاد خاصّ.
2. **أولويّة الكاشير مقابل أودو:** أوصي بتقديم **الكاشير (الموجات ١→٤)** لأنه بلا اعتماد خارجيّ ويسلّم قيمة تشغيليّة مباشرة؛ وأودو (٥→٦) بالتوازي متى توفّر حساب Cloudflare.
3. **عمق القاعدة المحلّية:** هل الهدف كاشير مثبَّت يعمل أوفلاين (تكفيه الموجة ١+٤) أم استقلالٌ تامّ عن السحابة (يستلزم الموجة ٧)؟
4. **توقيت استضافة أودو حقيقيّة** — يفتح المزامنة اللحظيّة (الموجة ٦).

### حسابات/تفعيلات مطلوبة منك (لا أستطيع فعلها)
- **حساب Cloudflare مجانيّ** لنشر الوسيط (يفتح المزامنة الدوريّة وإرسال المستندات).
- **مستخدم تكامل `bz_integration`** في أودو بمفتاح API مقيَّد.
- لاحقًا: **استضافة أودو على عنوان عامّ** (المزامنة اللحظيّة) + **Blaze** (نسخ مجدول أقوى وبديل Cloud Function — معلّق على تجديد البطاقة).
