# تقرير إنقاذ الشجرة المتسخة — السبب الجذريّ والعمل المؤمَّن

**التاريخ:** 2026-08-12 · **المنفّذ:** Claude · **يُكمّل ولا يلغي:** [`تقرير-جرد-الشجرة-المتسخة-2026-08-12.md`](تقرير-جرد-الشجرة-المتسخة-2026-08-12.md)

> لم يُحذف ملفّ واحد، ولم يُنفَّذ `reset` ولا `clean` ولا `restore` ولا `stash`، ولم تُزَل worktree.
> كلّ ما جرى: **ضبط إعدادٍ واحد، وإنشاء كومِتات ومراجع وحزم ونُسخ.** كلّه إضافيّ وقابل للعكس.

## ١. السبب الجذريّ — تصحيحٌ لتشخيصٍ سابق

التقرير السابق وصف المشكلة بأنّها «مرجع Codex داخليّ صفريّ غير صالح» واقترح حذفه بعد حجرٍ صحّيّ.
**المرجع لم يكن فاسدًا قطّ.** السبب الحقيقيّ:

```
طول مسار المرجع = 292 حرفًا   |   حدّ ويندوز MAX_PATH = 260
```

`git fsck` يقولها حرفيًّا قبل أن يشتكي من الـsha:

```text
warning: failed to stat '.git/refs/codex/turn-diffs/checkpoints/…': Filename too long
error: … invalid sha1 pointer 0000000000000000000000000000000000000000
```

الصفر ليس قيمة المرجع؛ هو ما يراه Git حين يعجز عن قراءة الملفّ أصلًا.

### من أين جاء الطول؟

| الجزء | الأحرف |
|---|---:|
| مسار المشروع `…\Desktop\العمليات اليومية\BrandZo HUB\warehouse-system-main\.git\` | ٧٨ |
| `refs\codex\turn-diffs\checkpoints\` | ٣٤ |
| هاش الجلسة (٦٤) + هاش الدور (٦٤) + ختم زمنيّ (١٣) + UUID (٣٦) + فواصل | ١٨٠ |
| **الإجمالي** | **٢٩٢** |

### لماذا كان الحذف سيفشل

المرجع المعطوب **يتغيّر مع كلّ دورة عمل**: وقت جرد Codex كان
`…/769cca87…/1786529029919/ce36201f-…`، وعند فحصي صار
`…/3602fb5e…/1786542210011/b3a4ef34-…`. أي أنّ آلية checkpoint تُعيد إنتاج العطل،
وحذف مرجعٍ بعينه علاجٌ للعرَض يعود بعد ساعة.

### الإصلاح المنفَّذ

```bash
git config core.longpaths true
```

على المستودع المشترك (ترثه كلّ الـworktrees). النتيجة **قبل/بعد**:

| الفحص | قبل | بعد |
|---|---|---|
| `git show-ref` | خروج 128 · `bad ref` | **خروج 0** · ١٣٥ مرجعًا |
| `git fsck --no-reflogs` | خروج 2 · `invalid sha1 pointer` | **خروج 0** · بلا أخطاء |
| `git fetch origin` | كان يفشل | **خروج 0** |
| المرجع «الفاسد» | `0000000…` | **`4d09f45` — كائن tree سليم** |

**لم يُحذف أيّ مرجع.** المحتوى كان سليمًا طوال الوقت خلف حاجز MAX_PATH.

## ٢. تصحيحٌ منهجيّ: «الكائن موجود» ≠ «العمل محفوظ»

أوّل جردٍ آليّ بنيته استعمل `git cat-file -e <blob>` وأعطى نتيجة مطمئنة كاذبة:
«١٤٥ من ١٤٦ ملفًّا محفوظة في Git». الاختبار خاطئ — وجود الكائن في المخزن يعني فقط
أنّ أحدًا نفّذ `git add` يومًا ما، والكائن السائب يُمحى بـ`git gc --prune`.

الاختبار الصحيح هو **البلوغ من مرجع**:

```bash
git rev-list --all --objects | awk '{print $1}' | sort -u
```

وبعد تطبيقه انقلبت النتيجة: **١٥٣ ملفًّا (٥٠٫٤ م.ب) لا يبلغها أيّ كومِت في أيّ فرع.**

### تفصيل الكود الذي كان مفقودًا فعلًا

من الملفّات الستّة التي صنّفها التقرير السابق «كودًا غير مرفوع»، أربعة كانت **مطابقة
لـmain** (الفارق كان سطرًا فارغًا في نهاية الملفّ وحده — ما ظهر «فرقًا كاملًا» كان
اختلاف CRLF/LF). المفقود حقيقةً اثنان فقط:

- `src/pages/dashboard/general-manager-operations-briefing.astro` (٧٧٣ سطرًا)
- `src/services/briefing/gmReviewService.js` (٣٦ سطرًا)

ومعهما سطر تنقّل واحد وقاعدة `gm_review`. طُبّقت **النيّة لا الملفّات**: الشجرة الأصلية
متأخّرة ٧١ كومِتًا، فأُضيف الجديد فوق `main` الحالية بدل نسخ الملفّات القديمة كاملة.

## ٥. ما لم يُنفَّذ عمدًا — ينتظر قرار المالك

1. **حذف أو نقل أيّ ملفّ من الشجرة الأصلية.** النسخ مؤمَّنة، والأصل كما هو.
2. **نشر `firestore.rules`** بقاعدة `gm_review` الجديدة — النشر قرار المالك وحده.
3. **دفع أيّ فرع إلى `main`** — بما فيه فرعا الإنقاذ.
4. **إزالة أيّ worktree** — لا واحدة قابلة للتقليم الآليّ، و١٦ منها تحمل عناصر محلّية.
5. **نقل المستودع لمسارٍ أقصر** — يبقى خيارًا إن عاد العطل رغم `core.longpaths`.

## ٦. توصية دائمة

`core.longpaths` مضبوط على هذا المستودع فقط. أيّ **clone جديد** على هذا الجهاز
سيعيد إنتاج العطل نفسه ما لم يُضبط عليه، أو يُضبط عامًّا:

```bash
git config --global core.longpaths true
```

وهذا تغييرٌ في بيئة المالك — لم يُنفَّذ بلا إذنه.
